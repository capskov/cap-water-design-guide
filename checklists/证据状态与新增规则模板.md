# 规则扩展协议：像树一样加分支，不把所有案例塞进一篇文字

对新方案先创建卡片文件 `examples/YYYYMMDD_项目_场景.md`，格式：

```yaml
id: CAP-CASE-YYYYMMDD-001
project: 项目名称
stage: 方案/初设/施工图/审查
file_baseline: 明确文件名称和版本
scenario: 道路穿越 / 河道 / 排气井 / 计量 / 套管 / 套价
observed_design: 原文件明确的方案和尺寸
rationale: 当时为什么采用
rule_candidate: 可以抽象的一般判断
status: historical_observation | confirmed_project | pending_external_verification
technical_references: [标准号-条文号, 图集号及页码]
exceptions: 哪些条件不能复制
price_or_quantity_boundary: 计价范围
review: 需补证事项
```

## 状态管理
- `historical_observation`：历史资料载明，未证明在其他地区通用。
- `confirmed_project`：该工程已确认条件，可用于本项目继续工作。
- `pending_external_verification`：现行规范、图集、权属许可、结构/水力计算未完成，不能自动定型。

## 文件更新顺序
1. 先写案例卡片和来源。
2. 若跨项目重复出现且不与现行规范冲突，再抽象到对应`references/`专题。
3. 有新场景分支才改`references/01_场景决策树.md`及`README.md`决策树。
4. 改井位原则时同步改`references/02_节点井室与间距.md`。
5. 改章节计价时必须记录标准版本、生效时间与子目工作内容。
6. 在`CHANGELOG.md`写变更、来源、是否影响既有项目；绝不静默覆盖历史案例或V1.0。


## V3.0 核心维护格式

新增经验须说明：场景与触发条件、技术目的、为什么合理、什么时候应该简化或改变、对投资的影响、引用证据与待核之处。历史实际做法不能自动升格为规范。若属于非公开原始工程资料，应保留内部来源，只发布匿名条件示例。
